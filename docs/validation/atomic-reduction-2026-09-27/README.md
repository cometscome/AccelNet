# Force atomic reduction — revision 1.11

Baseline: `gpu` **0e79af3**, AccelNet **1.0.1**. See the mathematical ownership
argument in [speedupmethods.md, Section 22](../../../speedupmethods.md#22-remove-fine-grained-force-atomics-revision-111).

## What changed

* Host G5 pair-once force evaluation assigns an entire center's CSR edge range
  to one worker. No other worker writes those edge-force slots, so both sides
  of a pair can be accumulated without atomic instructions.
* Host physical-atom scatter is a serial streaming pass without per-edge or
  per-center atomics. Descriptor/NN/force computation remains threaded.
* GPU physical-atom force scatter retains its atomic additions. Different
  centers can share a target atom, including periodic and MPI ghost indices.
* GPU virial assembly uses a nine-component OpenMP reduction instead of nine
  explicit atomic additions per center. Runtime reduction may use atomics
  internally; this is not a claim of zero synchronization in the runtime.
* `src/shared/generic_force_edge_body.inc` contains the single numerical body.
  The host center-owned include is generated by stripping only atomic directives
  from that body. The GPU edge schedule preserves its original guarded directives,
  which are inactive because `pair_once` is false. There is one maintained
  formula implementation; the two execution schedules are deliberately different.

The normal CPU batch and LAMMPS CPU APIs remain OpenMP-disabled. The host
thread timings explicitly use the optional target API with `use_host=.true.`.
No new reverse neighbor list or per-thread full force array is allocated.

## Protocol

GNU Fortran 11.4, `-O3`, FP64; Intel Xeon Gold 6526Y. Physical cores 6--13 are on
one socket/NUMA node. Compare OpenMP **OFF/1** against **ON/1/2/4/8**; dynamic
teams and nested parallelism are disabled, with explicit core binding.
`OMP_WAIT_POLICY=PASSIVE`, `GOMP_SPINCOUNT=300000`. GPU is H100 NVL, NVIDIA HPC
SDK 25.3, `-fast -O3 -mp=gpu -gpu=cc90,cc120`, mandatory device execution.

Both revisions use the prepared host/target API on fixed CSR environments with
64 supplied neighbors per center. High-order G5 rescales all 64 inside Rc;
the older Chebyshev/low-order fixtures retain their existing geometry. These
are synthetic inference measurements, **not LAMMPS step times**. GPU wall time
includes transfers, descriptors, NN and force/virial assembly. Model setup and
initial workspace allocation are warmed before timing.

Before/after binaries execute in alternating, reversed process order. Each
process records five warmed samples, at least 0.05 seconds per sample or one
full evaluation. Tables use the median of ten samples. The core warms for 20
seconds; CPU/GPU clocks are not locked. No builds or other tests run during
performance measurement. All E/F/virial components are checked against the
retained independent CPU reference before and after every timed sample.
Per-round medians and raw stage samples are retained, so variability is visible.

The eight-thread path improves by 1.03--1.48× in this sweep. GPU before/after
changes are within 0.5%; this change primarily benefits CPU threading. Scaling
is not monotonic: small/cheap cases still lose to OFF/1 at some thread counts.
The ON/1 and eight-thread comparisons and all stage samples are in
[performance.json](performance.json). Its `passed` flag denotes numerical and
protocol checks, not a universal performance threshold.

CPU clocks are **not fixed**. The separate [ownership probe](ownership-probe.json)
observed 3.9 GHz and 2.8 GHz operating points, explaining large wall-time shifts
between runs. For G5 direct at comparable 2.8 GHz, OFF/1 measured 241.1--241.9 ms
before and 242.2--242.9 ms after; at 3.9 GHz it measured 173.3 versus 173.7 ms.
Those matched-frequency observations differ by less than 1%. Across the final
six-case sweep OFF/1 changes range from -2.8% to +5.0%; do not interpret the
unlocked-clock timings as precise intrinsic instruction-cost changes.

### Why the host scheduling wrapper matters

An intermediate implementation used a native `parallel do` for center-owned
forces while other stages used host target teams. With eight requested threads,
that combination left **15 live threads** and slowed even the unchanged
descriptor stage. Using host target teams consistently restores eight live
threads. The probe measured aggregate eight-thread medians of 180.8 ms for the
rejected persistent-pool trial, 163.8 ms before this revision, and 135.2 ms for
the final schedule. Raw clocks, thread counts and per-round times are retained;
these aggregates span different operating frequencies. The serial kernel's
`.text` is byte-identical across this scheduling fix (hash in the atomic audit).
See also [rejected-persistent-pool.json](rejected-persistent-pool.json).

### Separate n2p2 performance gate

The existing three CPU performance CTests passed (common CPU/reference,
low-order G5 moment advantage, and order-scaling smoke). A separate strict
n2p2 direct-parity sweep, six rounds with 0.3-second samples, **failed for type
21**: AccelNet CPU/n2p2 = **1.101346**, just above the unchanged 1.10 limit.
Types 2, 3 and 22 passed that limit; all numerical checks passed. Type 21 CPU
is 1.4% slower than the preceding measured AccelNet revision. This borderline
miss remains recorded rather than weakening the threshold or calling the whole
performance suite green. See [n2p2-direct-performance.json](n2p2-direct-performance.json)
and its [failure log](n2p2-direct-performance.log).

## Validation

* 50 GNU functional CTests passed. The last host scheduling adjustment leaves
  the serial numerical object byte-identical; final host 2/8-thread suites and
  independent H100/Blackwell checks were rerun after that adjustment.
* At both 2 and 8 host threads: 209 G5 checks, 137 other-descriptor checks,
  and the Chebyshev quick finite-difference test passed. Maximum E/F/virial
  difference is 2.23e-16 (rounded upper bound).
* GNU bounds-check build: 209 G5 checks passed.
* The same G5/other/quick suites passed on H100. Independent n2p2 high-order
  two-element and mixed four-element/all-type models passed on 8 host threads,
  H100 and Blackwell, including independent force and strain finite differences.
* LAMMPS: 21 CPU/GPU comparisons passed with 1/2 MPI ranks, orthogonal,
  triclinic and empty-rank cases, and GPU neighbor modes no/yes/hybrid.
* H100 Compute Sanitizer on the final Chebyshev quick case: **0 errors**.
* The compiled GNU **host center-owned** force function contains zero `lock`
  instructions, versus locked host accumulation in revision 1.10. See
  [atomic-audit.json](atomic-audit.json). The only active explicit atomic additions
  are in GPU physical-atom force scatter. The two guarded pair additions in the
  common source are stripped for host center ownership and inactive in the edge
  schedule; they remain for NVHPC code-generation stability.

## Reproduction

Build OFF and ON host instances as described in
[openmp-target.md](../../openmp-target.md#cpu-openmp-thread-comparison). Archive
the three baseline executables at commit `0e79af3` before rebuilding.

```sh
CUDA_VISIBLE_DEVICES="$H100_UUID" \
python3 AccelNetPredictor/benchmark/compare_atomic_reduction.py \
  --before-serial "$OLD_SERIAL" --before-openmp "$OLD_OPENMP" \
  --before-gpu "$OLD_GPU" --serial "$NEW_SERIAL" --openmp "$NEW_OPENMP" \
  --gpu "$NEW_GPU" --cores 6 7 8 9 10 11 12 13 \
  --rounds 2 --seconds .05 --output /tmp/atomic-performance
```

Early trials passed numerical tests but slowed low-order G5 direct by about
22%. Removing the extra GPU loop alone did not recover performance. Nsight
Systems isolated the regression to the force kernel, with unchanged launch
dimensions/register count and almost unchanged final scatter time. Retaining
the original guarded GPU directives restored performance; host center ownership
uses the same body with those directives stripped at build time. The exact
NVHPC optimization responsible is not established. See the [timing diagnostic](rejected-nested-loop.json)
and [kernel profile](profile-summary.json); these rejected trials are not the
final implementation.
