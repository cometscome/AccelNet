# モーメント構築の処理順序とデータ再利用の診断

この診断後、処理順序変更と力計算の最適化を[正式実装へ取り込んだ](../../gpu-moment-force-2026-09-26/README.md)。
以下は診断時点の記録。

**大きい系でのmomentの効率低下は、構築カーネルの仕事の並べ方を変えるだけで大幅に改善した。**
同じデータを短い間隔で再利用できないことと、隣接GPUスレッドの読出位置がばらけることが、
現行実装の主な問題と判断する。L2ミス率そのものはカウンタ権限の制限により未測定。

これは原因分析のための隔離した診断版。既存のGPU/CPU計算ソースと配布済みlmpは変更していない。
既存lmpのSHA256は `6fb237a8c912d811423d1d23d5e74a949f2e8fc66aebe307173c22f1688d28b3` のまま。

## 変更したもの・固定したもの

元のモーメント構築は次の順序の仕事を`collapse(2)`でGPUに渡す。

```fortran
do component = 1, 84
    do atom = 1, N
        ! この原子の近傍を走査して1成分を構築
    end do
end do
```

隣接スレッドは別々の原子を担当する。同じ原子の次の成分の仕事は、線形仕事番号でN個先にある。
GPUがすべての仕事を厳密にこの順番で実行するという意味ではないが、同じデータを使う仕事が離れている。

診断版では原子をT個ずつまとめ、T=1/32/128/512を比較した。

```fortran
do atom_tile = 1, ceil(N/T)
    do component = 1, 84
        do atom_in_tile = 1, T
            ! 近傍の加算順序・計算式は元と同じ
        end do
    end do
end do
```

T=1では、隣接スレッドの多くが同じ原子の別の成分を処理する。
T=128では1ブロックの128スレッドが元と同じように同一成分・隣接原子を処理し、
同じ原子群の次の成分が隣接ブロックに配置される。
したがってT=128の効果は、warp内の読出位置の変更だけでは説明できず、原子群の再利用間隔の短縮を支持する。
T=1ではさらに、warp内の複数スレッドが同じ幾何・cutoffデータを読むため、
同じメモリ領域へのアクセスをまとめやすくなる。

計算するモーメント数・各成分の近傍走査回数・倍精度・加算順序・配列の形状・モデルは同じ。
ソース変更は構築カーネルのループ順序と添字計算、端数原子のガードのみ。
結果の書込み先は各原子・成分で一意であり、新たなatomicやreductionは使っていない。

## 24,000原子での結果

H100 NVL、Ti/O、角度次数6、84成分、1 rank、GPU近傍。
総時間は20 step warmup + 100 stepを各2回、実行順を反転した中央値。
構築カーネル時間はNsight Systemsで100回の平均（別途各1回計測）。

| 原子のまとめ方 | 構築カーネル ms | LAMMPS総時間 ms/step |
| --- | ---: | ---: |
| 元の順序（全原子を成分ごとに処理） | 12.358 | 25.205 |
| 512原子ごと | 4.335 | 17.144 |
| 128原子ごと | 2.659 | 15.474 |
| 32原子ごと | 2.005 | 14.828 |
| 1原子ごと | 1.037 | 13.863 |

元の順序→1原子ごとで構築は約11.9倍、全体は約1.82倍高速化した。
元とT=1/32は、ブロック数15,750・128スレッド/ブロック・48レジスタ/スレッドで同一。
T=128/512は端数のパディングで15,792ブロック、それ以外は同じ。全てlocalMemoryPerThread=0。
同じサイズでの理論上の並列仕事数とレジスタ使用量が同じなので、単なる並列度増加や
レジスタ削減による改善とは考えにくい。

また、構築以外のカーネル時間はほぼ同じだった。

| 処理（24,000原子） | 元の順序 ms | 1原子ごと ms |
| --- | ---: | ---: |
| 幾何・動径・方向の累乗 | 3.476 | 3.469 |
| モーメント構築 | 12.358 | 1.037 |
| 記述子への変換 | 0.219 | 0.221 |
| NN・係数変換 | 0.138 | 0.139 |
| 近傍ごとの力 | 6.506 | 6.502 |
| 力・virial集計 | 0.452 | 0.451 |

5,184→24,000原子（4.63倍）で、元の構築は1.232→12.358 ms（10.03倍）だったが、
T=1では0.262→1.037 ms（3.96倍）となった。元の超線形な悪化は解消している。

## なぜ元の並べ方が不利か

入力はCSR近傍リストなので、原子ごとに近傍の格納領域が離れている。
隣接スレッドが別の原子の同じ番号の近傍を読むと、読出アドレスが離れ、
1つのwarpのアクセスを少数のメモリ要求にまとめにくい。
さらに元の順序では、次のモーメント成分で再利用するまでに、他の多くの原子のデータを読む。
大きい系では、この間にキャッシュから追い出されやすい。

出力`moments(atom,component,spin)`の連続書込みには元の順序が適しているが、
各原子・成分が書くのは倍精度2値（16 byte）である。
一方、入力はこの構造で平均約137近傍の距離と、約50角度近傍のcutoff・種重み・方向の累乗を読む。
ソース上の単純な読出要求は約3 KB/原子/成分に相当し、入力読出し側の最適化が重要。
これはDRAMから実際に転送されたbyte数ではなく、キャッシュ共有やコンパイラ最適化前の概算。

## キャッシュ容量との整合性と限界

CUDA driver APIで対象H100のL2容量62,914,560 byte（60 MiB）、SM数132を確認した。
前回失敗した性能カウンタ取得を繰り返したり、GPUドライバ設定を変更したりしていない。

初期構造でskin込み7.1 Å近傍数は平均137.17、角度5 Å内は平均50.17。
幾何配列の実辺数分は`7 * edges * 8` byte、1成分が参照する方向の累乗3列は
`3 * edges * 8` byteに対応する。配列の参照範囲の上限概算は合計で
5,184原子なら約56.9 MB、24,000原子なら約263.4 MB。
大きい系では1成分の処理だけでもL2容量を大きく上回る配列範囲を走査する。

これは実測キャッシュ占有量ではない。累乗は角度カットオフ外を読まず、
幾何配列も全フィールドは読まない。逆に実際の転送はキャッシュライン単位であり、
他の配列の出入り・L1・GPUのブロック配置も影響する。
「特定原子数でL2が満杯になる」と断定するものではない。
性能カウンタがないため、L2ヒット率・DRAM帯域・L1やwarp内の共有の寄与は未分離。
ただし、T=512→128→32→1と再利用を近づけるほど改善する制御実験は、
データ再利用とメモリアクセスの配置が主要因であることを強く支持する。

## 数値検証と残る作業

非プロファイル40実行、プロファイル6実行の比較がすべて合格。非プロファイルの最大力差は1.58e-13 eV/Å、原子別エネルギー差は2.27e-13 eV。

最終全原子の力・原子別エネルギー・座標を`atol=2e-8, rtol=2e-9`で比較し、
非プロファイルではthermoの全体エネルギー・virialも`atol=2e-5, rtol=2e-9`で比較した。
演算式・各成分の加算順序は同じだが、コンパイル時の最適化や力集計の実行順で丸め差がある。

今回の診断版はこのモデル・H100での原因切り分け用。
正式採用時は、異なる次数・複数種・auto/direct混在・他GPU・MPI・空rankなどの既存テストを再実行する。
T=1が全モデル・GPUで最善とまでは判断しない。
この改善後は力計算6.5 msと幾何処理3.5 msの比率が大きくなる。
